Technical Concepts Deep Dive

Every engineering concept an ADM needs to discuss fluently — explained in plain English with real-world context.

By Richard Reyes · Read sequentially the first time, use as reference after

Part 1

The Software Development Lifecycle 3 concepts

The stages every piece of software goes through. AI tools touch each stage differently — know where they help, where they’re risky, and where they don’t apply.

Requirements → Design → Build → Test → Deploy → Operate

What it is

The six stages of building software. Requirements: what should it do? Design: how will we architect it? Build: writing the code. Test: verifying it works. Deploy: shipping it to real users. Operate: monitoring, incidents, performance tuning.

Why it matters

Cursor primarily accelerates Build and Test. But AI-generated code can create problems in Deploy (more rollbacks) and Operate (performance issues, memory leaks, incidents). An ADM who only talks about Build is missing where the real pain shows up.

How to talk about it

“Cursor accelerates build and test, but we also need the downstream stages — deployment and operations — to have the right guardrails. That means performance testing, progressive rollouts, and observability. AI makes code faster to write; the rest of the pipeline needs to keep up.”

Sprints and Agile

What it is

Most modern teams work in short cycles called sprints (typically 2 weeks). Each sprint has a goal, tasks, and a deliverable. At the end, the team reviews what shipped and plans the next sprint. This iterative approach is Agile (vs. “Waterfall,” where all requirements are defined upfront).

Why it matters

You fit Cursor adoption into existing sprint rhythms. Don’t introduce a new tool mid-sprint on a critical deadline. The best time is at the start of a sprint, with a specific task designated for the pilot.

Pull Requests (PRs) and Code Review

What it is

When a developer finishes a feature, they create a pull request (PR) — a proposal saying “here’s what I changed, please review it.” Other developers review, comment, request changes, and eventually approve. Only then does it merge into the main codebase.

Why it matters

PRs are the quality gate between “code written” and “code shipped.” If reviewers rubber-stamp AI-generated PRs because they look clean, bugs slip through. Key question: “Are your reviewers reviewing AI-generated code with the same rigor as human-written code?”

Real-world example

A team ships PRs 30% faster with Agent mode, but rollback rate increases. Investigation reveals reviewers were approving faster because AI code looked professional — well-formatted, good variable names — but they weren’t scrutinizing the logic.

Part 2

Code & Architecture 6 concepts

How software is structured and why it matters when AI generates code at scale.

Frontend, Backend, and Full-Stack

What it is

Frontend: the part users see (web pages, mobile screens). Built with React, TypeScript, HTML/CSS. Backend: server-side logic users don’t see — databases, APIs, authentication. Built with Go, Python, Java, Node.js. Full-stack: works on both.

Why it matters

Different teams have different Cursor use cases. Frontend teams benefit from component generation and UI consistency. Backend teams care about API correctness, query performance, and security. You position the tool differently depending on who you’re talking to.

APIs (Application Programming Interfaces)

What it is

A contract between two pieces of software. When a weather app shows the forecast, it calls a weather service’s API — sending a structured request and getting a structured response. APIs define: what you can ask for, how to ask, and what you’ll get back.

Why it matters

API contract inconsistency (Q35) is a classic AI problem. Different Agent sessions generate different (but individually valid) response formats. The fix: OpenAPI specs referenced in Rules so every endpoint follows the same format.

How to talk about it

“APIs are the contracts between services. When AI generates endpoints independently, those contracts can drift. We recommend an OpenAPI spec referenced in Rules so every generated endpoint follows the same format.”

Databases and SQL

What it is

Databases store persistent data. SQL (Structured Query Language) reads and writes data in relational databases (PostgreSQL, MySQL). Key performance concepts:

  • Indexes — Like a book’s index: lets the database find rows without scanning every row. Without an index on a 500M-row table, every query scans all 500M rows (a full table scan).
  • N+1 queries — Fetching a list, then making a separate query per item. 1,000 items = 1,001 queries instead of 2. Invisible at small scale; devastating at production scale.
  • Table locks — Large operations can lock a table, blocking all other operations until the lock releases. In production, everything queues up and times out.
Real-world example

An AI-generated query joins two 500M-row tables without filtering. In dev (1,000 rows): 5ms. In production: tries to process 250 trillion combinations, exhausts memory, locks the table for 20 minutes.

Microservices vs. Monoliths

What it is

Monolith: entire application is one codebase, deployed as one unit. Simpler to start; harder to scale independently. Microservices: application split into many small, independent services (user service, payment service, notification service), each with its own deployment.

Why it matters

In microservices, architectural drift (Q31) is a bigger risk because each service evolves independently. Governance via shared Rules and templates matters more.

Architectural Drift

What it is

Over time, different parts of a codebase use different patterns for the same problem. One service handles errors with try/catch; another uses result types; a third uses middleware. Each works, but inconsistency makes the codebase harder to understand and maintain.

Why it matters

Agent mode solves each task in isolation. Without explicit instructions pointing to canonical patterns, it draws from training data — which contains thousands of valid approaches. Different developers providing different context get different implementations.

How to talk about it

The fix: pattern-specific Rules pointing to template files (“follow the pattern in services/_template/endpoint.go”), golden templates, and periodic architecture reviews.

Middleware and Execution Order

What it is

In web applications, middleware is code that runs in a chain before a request reaches its main handler. Each middleware does one thing: rate limiting, authentication, authorization, logging. The order matters: rate limiting before auth protects against floods; rate limiting after auth lets attackers overwhelm the auth system.

Why it matters

AI refactoring might reorder middleware for “cleanliness” without knowing the order is security-critical (Q32). The fix: explicit Rules documenting the order, integration tests that validate the sequence, and AI-restricted zones for security code.

Part 3

Testing Layers 7 concepts

Testing is where AI tools create the most subtle problems. Understanding each layer — and its blind spots — is critical.

Unit Tests

What it is

Tests that verify a single function in isolation. Fast (milliseconds), deterministic, and mock all external dependencies. Example: verify that add(2, 3) returns 5.

Why it matters

AI is excellent at generating unit tests but tends to generate too many (Q33) and make them too shallow (Q30). A test that checks add(2, 3) == 5 doesn’t test what happens with null, Infinity, or a string.

Integration Tests

What it is

Tests that verify how multiple components work together. Instead of testing “add” alone, verify that when a user submits a form, the API receives the data, validates it, stores it in the database, and returns the correct response.

Why it matters

Integration tests catch bugs in the seams between components — exactly where unit tests don’t reach. AI tools are less reliable at generating these because they require understanding how the full system connects.

End-to-End (E2E) Tests

What it is

Tests simulating a real user: a browser automation tool clicks buttons, fills forms, navigates pages, and verifies results — as if a human were using the product.

Why it matters

E2E tests catch the most realistic bugs but are slow and fragile. They’re the top of the testing pyramid — few in number, covering critical user journeys. AI rarely generates good E2E tests because they require understanding user workflows, not just code.

Contract Tests

What it is

Tests verifying the agreement between two services. If Service A expects { user: { id: 123, name: "Alice" } } from Service B, a contract test verifies Service B actually returns that shape — and that Service A handles it correctly.

How to talk about it

“Contract tests validate that two services agree on the data format between them. When AI generates endpoints independently, contract tests are the safety net that catches format inconsistencies before deployment.”

Visual Regression Tests

What it is

Tests that screenshot UI components and compare them pixel-by-pixel against a baseline. If a code change moves a button 3 pixels or changes a font color, the test flags it.

Why it matters

For frontend-heavy companies (Figma, Adobe), AI-generated UI code might subtly alter styling without breaking functional tests. Visual regression tests catch what functional tests miss.

Load Testing

What it is

Simulating thousands of concurrent users to measure performance under stress. Tools like k6, Locust, or JMeter send high request volumes and measure response times, error rates, and resource consumption.

Why it matters

AI-generated code that works at small scale often fails under load (Q29, Q38). Load testing in staging catches performance regressions before production.

Test Tiering in CI

What it is

Organizing tests by speed and running them at different stages:

TierWhatWhenSpeed
Tier 1Unit testsEvery commitSeconds
Tier 2Integration testsEvery PRMinutes
Tier 3E2E + load testsNightly / pre-releaseHours
Why it matters

When AI quadruples the test suite (Q33), running everything in one stage makes CI unbearably slow. Tiering keeps feedback fast for developers while still running comprehensive tests before deployment.

Part 4

CI/CD & Release Safety 5 concepts

The automated systems that stand between “code written” and “code in production.”

CI (Continuous Integration)

What it is

An automated system that runs on every code push: compiles, runs tests, checks linting, scans for vulnerabilities, and reports pass/fail. Common tools: GitHub Actions, Jenkins, CircleCI, GitLab CI.

Think of it as: A rigorous automated inspector checking every piece of work before it enters the building.

Why it matters

CI is the automated quality gate. When AI accelerates code production, CI must scale to match. If the pipeline takes 45 minutes but PRs arrive every 20 minutes, the pipeline becomes the bottleneck.

CD (Continuous Deployment / Delivery)

What it is

Continuous Delivery: code is always ready to deploy but requires a human to push the button. Continuous Deployment: code deploys automatically after CI passes.

Why it matters

The faster code auto-deploys, the more important CI quality is. If AI-generated code passes CI (because tests are shallow) and auto-deploys, bugs reach production instantly.

Canary Deployments

What it is

Instead of deploying to all users at once, deploy to 1–5% first. If metrics look healthy (no errors, no latency increase), gradually expand. If something breaks, only 1% of users are affected.

Think of it as: The canary in the coal mine — a small group that signals danger before it spreads.

How to talk about it

“Progressive rollouts — canaries, percentage-based releases — give you a production-grade safety net. Instead of shipping to 100% and hoping, you validate with real traffic at 1% and only expand when metrics are clean.”

Feature Flags

What it is

A toggle that lets you turn a feature on or off without deploying new code. Enable for specific users, a percentage of traffic, or specific environments. If problems arise, flip the flag off — no deployment needed.

Why it matters

Feature flags decouple “shipping code” from “enabling features.” Developers can merge AI-generated code immediately (avoiding long branches and merge conflicts — Q39) but keep it hidden until validated.

Rollbacks

What it is

Reverting a deployment to the previous known-good version when production breaks. The emergency brake.

Why it matters

Rollback rate is a quality signal. If it rises after AI adoption (Q36), code is reaching production with undetected issues. The fix: strengthen quality layers, not slow down.

Part 5

Performance & Reliability 6 concepts

The production problems that surface when AI-generated code meets real-world scale and load.

The N+1 Query Problem

What it is

Code makes 1 query to fetch a list, then N separate queries to fetch related data for each item. 1,000 items = 1,001 queries instead of 2.

Bad: N+1 pattern (101 queries for 100 orders)

orders = db.query("SELECT * FROM orders LIMIT 100") for order in orders: customer = db.query("SELECT * FROM customers WHERE id = ?", order.customer_id)

Good: Batch pattern (2 queries for 100 orders)

orders = db.query("SELECT * FROM orders LIMIT 100") customer_ids = [o.customer_id for o in orders] customers = db.query("SELECT * FROM customers WHERE id IN (?)", customer_ids)
Why it matters

Agent mode solves for correctness, not performance. The N+1 pattern returns the right data — it’s just hundreds of times slower at scale. Fix with Rules: “always use batch queries instead of loops.”

Memory Leaks

What it is

A program allocates memory but never releases it. Over time, usage grows until the process crashes.

Common causes in AI-generated code:

  • Event listeners never cleaned up — Agent adds a listener in a repeatedly-called function. Each call adds one; none are removed.
  • Caching without eviction — In-memory cache with no max size or expiration. Grows forever.
  • Connection pool exhaustion — Each call opens a new DB connection but doesn’t release it.
Why it matters

Unit tests run in milliseconds — no time for leaks to accumulate. Leaks only surface under sustained load (hours/days). Fix: resource management Rules + sustained load testing in staging.

p95 Latency

What it is

The response time that is faster than 95% of all responses. If p95 is 400ms, 95% of requests complete within 400ms. Teams track p95 (or p99) because averages hide outliers. An average of 50ms might mask 5% of requests taking 3 seconds.

Why it matters

If AI-generated code introduces slow queries, p95 often degrades before the average does — it’s an early warning signal.

APM (Application Performance Monitoring)

What it is

Tools monitoring real-time application performance: response times, error rates, query durations, memory/CPU usage, and request traces. Common tools: Datadog, New Relic, Dynatrace, Grafana.

How to talk about it

“APM gives you the observability layer to connect performance changes to specific code changes. When a team reports degraded response times after heavy Agent use, APM pinpoints which endpoints, queries, and PRs introduced the regression.”

Observability (Logs, Metrics, Traces)

What it is

The practice of understanding what’s happening inside a system, built on three pillars:

  1. Logs — Timestamped event records (“User 123 logged in at 14:32”)
  2. Metrics — Numerical measurements over time (CPU usage, error rate)
  3. Traces — Full path of a request through the system (frontend → API → auth → database → response)
Why it matters

When AI-generated code causes problems that tests missed, observability is the last line of defense that catches them in production.

Runbooks

What it is

Documented step-by-step procedures for handling specific incidents: “If the connection pool is exhausted, do X. If the payment service returns 500 errors, do Y.” Turns incident response from improvisation into a repeatable process.

Why it matters

An ADM can help teams create runbooks for AI-specific failure modes: “If you suspect AI-generated code caused a performance regression, here’s how to trace it with APM, identify the PR, and roll back.”

Part 6

Security & Governance 7 concepts

The controls, boundaries, and compliance frameworks that enterprise customers require before deploying AI tools.

VPC (Virtual Private Cloud)

What it is

A private, isolated network within a cloud provider (AWS, GCP, Azure). Resources inside a VPC communicate with each other; traffic to the outside internet is strictly controlled. Think of it as a walled compound with a guarded gate.

How to talk about it

“For customers with strict VPC requirements, we discuss self-hosted options so no code or telemetry leaves their network boundary. If evaluation takes time, we start a pilot on non-sensitive code while the self-hosted architecture is assessed.”

Least Privilege

What it is

Every person, system, or tool should have only the minimum access needed for its job. A frontend developer shouldn’t have production database credentials.

Why it matters

When configuring AI tools, least privilege means: the AI should only see the code relevant to its task, not secrets, credentials, or unrelated internal documentation. Rules and .cursorignore limit what the AI accesses.

Dependency Governance

What it is

Controlling which external libraries can be used. Every dependency is someone else’s code you’re trusting to work correctly, be secure, and be maintained. Supply chain attacks inject malicious code into popular libraries.

Common tools: Snyk (vulnerability scanning), Dependabot (auto-update PRs), Socket (suspicious behavior detection).

Why it matters

AI freely suggests dependencies without knowing the org’s approved list (Q40). Fix: Rules referencing an approved list, CI blocking unapproved additions, and scanning tools as a safety net.

CODEOWNERS

What it is

A repository file defining which people or teams must review changes to specific directories. If CODEOWNERS says “changes to services/auth/ require @security-team,” any PR touching auth code automatically requires that team’s approval.

Why it matters

Creates human coordination points for sensitive code. Prevents Q39 (parallel modifications without coordination) and Q32 (AI refactoring security code without security review).

Tenant Separation

What it is

In multi-tenant systems, ensuring Customer A’s data is completely isolated from Customer B’s. No query, bug, or misconfiguration should ever expose one tenant’s data to another.

Why it matters

For consulting firms (PwC, Deloitte), the AI must never learn from Client A’s code when working on Client B’s. Privacy Mode and admin controls are the key discussion points.

Compliance Frameworks (SOC 2, SOX, PCI-DSS, HIPAA, GxP)

What it is
  • SOC 2 — Security, availability, processing integrity, confidentiality, privacy controls
  • SOX — Financial reporting controls (public companies)
  • PCI-DSS — Payment card data security
  • HIPAA — Healthcare data protection
  • GxP — Good Practice regulations for life sciences (pharma, biotech)
How to talk about it

“AI-generated code flows through the same PR, review, and CI pipeline as human-written code. The audit trail is preserved: who created the PR, who reviewed and approved, what tests ran, when it deployed. For GxP or SOX environments, we add Rules requiring documented justification for each change.”

.cursorignore

What it is

A config file (like .gitignore) telling Cursor which files to exclude from its codebase index. Excluded files won’t be used as context for AI suggestions.

Why it matters

Two uses: (1) exclude deprecated code so AI stops referencing it (Q37), and (2) exclude sensitive directories from AI context for security. In regulated environments, .cursorignore is part of the security controls discussion.

Part 7

Metrics & ROI 7 concepts

How to measure AI tool impact and translate technical metrics into business outcomes.

Activation Rate

What it is

Percentage of licensed users meaningfully using the tool (beyond just installing it — actually using Agent, Chat, or Tab in real workflows).

Why it matters

200 seats but only 50 active users = 25% activation. This signals an enablement gap — an ADM’s core problem to solve.

Depth of Use

What it is

How deeply users engage beyond activation:

  • Light — Tab completions only
  • Moderate — Tab + Chat for Q&A and explanation
  • Deep — Agent mode + Rules + codebase-aware workflows
Why it matters

Depth correlates with perceived value and renewal likelihood. Moving users from Light to Deep is an ADM’s leverage point.

Cycle Time

What it is

Elapsed time from “work started” to “deployed in production.” Includes coding, review, CI, and deployment time.

How to talk about it

“If Cursor reduces average cycle time from 5 days to 3.5 days, that’s a 30% improvement — directly translatable to faster feature delivery and more roadmap capacity.”

PR Latency

What it is

Time between a PR being opened and being merged. Long PR latency signals review bottlenecks, large PRs, or unclear ownership.

Why it matters

AI should reduce PR latency. If it increases after adoption, something’s wrong — possibly larger PRs or review fatigue.

Rollback Rate

What it is

Percentage of deployments that need to be reverted. Healthy: under 5%. Rising rollback rate = code quality degrading.

Why it matters

The counter-metric to velocity. A team shipping 30% more PRs but with doubled rollback rate may have worse net quality. Always pair velocity metrics with quality metrics.

Escaped Defects

What it is

Bugs that “escape” the quality pipeline (tests, review, staging) and reach production.

Why it matters

AI-generated code with shallow tests creates more escaped defects. Tracking this over time shows whether quality guardrails are keeping up with AI-assisted velocity.

ROI Storytelling

What it is

Translating technical metrics into business outcomes:

Technical MetricBusiness Outcome
30% faster cycle timeShip features faster → faster time-to-market
45 min/day saved × 200 devs150 hours/day recovered capacity
25% fewer escaped defectsFewer incidents → lower cost, better customer trust
50% faster onboardingNew hires productive in 2 weeks instead of 4
How to talk about it

“We measure adoption internally, but the story for the CFO is different: recovered engineering capacity, faster delivery, and reduced incident costs. The key is translating developer experience metrics into the language of business outcomes.”

Part 8

Change Management & Rollout 4 concepts

How to deploy a tool across an organization without chaos.

Champion Model

What it is

Identify 3–5 enthusiastic, respected engineers per team/region. Give them early access, deeper training, and a direct feedback channel. They become local advocates who help peers — more effective than mandates or external trainers.

Why it matters

Engineers trust other engineers. A champion saying “this saved me 2 hours on that migration” outweighs any polished demo.

Multi-Wave Rollout

What it is
  • Wave 1 (Pilot) — 10–20 engineers, one team. Goal: prove value, identify issues, build the playbook.
  • Wave 2 (Expansion) — 3–5 teams. Goal: validate the playbook works across workflows.
  • Wave 3 (Scale) — Org-wide. Goal: standardize governance, measure aggregate ROI.
Why it matters

This is literally your deployment strategy. Each wave has different priorities: Wave 1 is learning, Wave 2 is proving repeatability, Wave 3 is governance and scale.

Enablement vs. Training

What it is

Training teaches how to use a feature (“here’s how Agent mode works”). Enablement helps integrate the tool into specific workflows (“here’s how to use Agent mode for your Go microservices”). Enablement is harder but stickier.

Why it matters

High activation but low depth = training happened but enablement didn’t. The team knows what Cursor can do; they don’t know how to make it work for their codebase.

Shadow AI

What it is

Employees using AI tools without organizational approval — personal accounts, browser tools, copy-pasting code to ChatGPT. Creates security and compliance risk because the org has zero visibility.

How to talk about it

“The question isn’t whether your engineers will use AI. It’s whether they’ll use it with guardrails or without. Managed deployment replaces shadow AI with governed AI.”

Part 9

Industry-Specific Concepts 4 concepts

Technical details that matter when engaging specific verticals.

Embedded Systems and C/C++

What it is

Computers built into devices — car dashboards, medical devices, IoT sensors, Samsung TVs, NVIDIA firmware. Programmed in C/C++ for precise hardware control and manual memory management.

Why it matters

AI handles C/C++ less well than web languages (less training data), build systems are custom, and testing requires hardware-in-the-loop. Be honest: embedded is a later-wave candidate, with early value in docs, test scaffolding, and CI scripting.

CUDA

What it is

NVIDIA’s framework for running code on GPUs instead of CPUs. GPUs run thousands of operations in parallel — essential for AI/ML training and scientific simulation. CUDA has unique constraints: thread management, memory hierarchy, synchronization.

Why it matters

NVIDIA engineers write CUDA code. AI coding tools are useful for scaffolding and standard logic, but not yet reliable for performance-critical kernel optimization. Position carefully.

GxP and Validation (Life Sciences)

What it is

Regulatory standards for pharma/biotech/medical devices requiring every change to be validated: documented, reviewed, tested, traced. GxP covers GMP (Manufacturing), GLP (Laboratory), and GCP (Clinical).

How to talk about it

“AI-generated code enters the same controlled change process. The audit trail — PR history, approvals, test results, deployment records — is preserved. For GxP environments, we add Rules requiring documented justification for each change.”

PMS (Property Management System)

What it is

Software that hotels use to manage reservations, check-ins, billing, and guest profiles. A PMS integrates with dozens of external systems: payment processors, booking platforms, loyalty programs, housekeeping, and door locks.

Why it matters

PMS environments are integration-heavy. AI helps write integration code, but AI-generated mocks of third-party systems may not represent real behavior. Strong contract and integration testing are essential.

Part 10

The Diagnostic Framework

When a customer describes a problem, use this mental model to diagnose it.

4-Step Diagnostic

  1. Where in the SDLC did it originate? — Build (bad pattern)? Test (shallow coverage)? Deploy (no canary)? Operate (no monitoring)?
  2. Why didn’t quality layers catch it? — Unit tests too shallow? Integration tests missing? Review rubber-stamped? CI not checking this class of issue? Staging doesn’t match production?
  3. What guardrail prevents it? — Rules? CI enforcement? Review process (CODEOWNERS)? Observability? Deployment strategy (canary, flags)?
  4. How do you frame it? — Acknowledge without blaming the tool. Explain the gap. Propose the guardrail. Connect to business outcome.
Example: Q29 — Performance Degradation

1. Originated in Build — AI generated N+1 queries.
2. Missed by Tests — Unit tests don’t test performance; staging had small data.
3. Guardrail: Performance Rules + load testing in CI + APM monitoring.
4. Frame it: “Bugbot catches correctness issues. Performance requires a different validation layer — we recommend performance-focused Rules and load testing in your CI pipeline.”

Example: Q34 — Memory Leaks

1. Originated in Build — Event listeners never cleaned up.
2. Missed by Tests — Unit tests are too short-lived to observe memory growth.
3. Guardrail: Resource management Rules + sustained load testing + heap profiling.
4. Frame it: “Memory leaks are invisible to short-lived tests. We add Rules requiring cleanup patterns and run sustained load tests in staging to catch growth before production.”

Example: Q30 — Production Bugs Despite Green CI

1. Originated in Test — AI-generated tests were happy-path only.
2. Missed by Review — Test files weren’t reviewed with the same rigor as production code.
3. Guardrail: Rules requiring edge-case tests + senior review of test files + contract tests at boundaries.
4. Frame it: “AI-generated tests increase coverage quantity. The team still needs to ensure coverage quality — testing the failure modes that only experience teaches you to anticipate.”
